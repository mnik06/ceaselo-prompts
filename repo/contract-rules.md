The command contract is exactly one JSON object of this shape:
{
  "lockfiles": string[],                       // files whose contents decide whether dependencies must be installed again
  "install": string, "build": string,
  "test": { "all": string, "affected": string | null },   // affected may use {base}
  "run"?: { "command": string, "readyUrl": string | null, "readyTimeoutS": number, "memoryMb": number },   // left out only when every surface below is driven by cli or none
  "deploy": string | null, "deployPreview": string | null,
  "verify": { "steps": { "name": string, "command": string, "kind": "typecheck" | "build" | "lint" | "test" | "other", "affected": string | null }[] },   // the floor, in order, fail fast; affected may use {base}
  "ledgers": { "name": string, "paths": string[], "regenerate": string }[],
  "db": { "template": string, "create": string, "drop": string } | null,   // three shell commands, see below
  "login": { "kind": "command", "command": string } | { "kind": "provided", "accounts": { "role": string, "emailKey": string, "passwordKey": string }[], "howTo": string } | { "kind": "none" },   // how sessions sign in, see below
  "ports": { "block": number, "env": { [ENV_NAME: string]: number } } | null,   // env name -> offset inside the block
  "toolchain": { "node": string | null, "packageManager": string | null, "flutter": string | null },  // see below
  "services": { "name": string, "scope": "repo" | "ticket", "start": string, "check": string, "stop": string | null, "memoryMb": number, "needs": ("docker")[], "configFiles"?: string[] }[] | null,   // local dependencies the stack needs running, see below
  "surfaces": { "surfaceId": string, "drive": "browser" | "cli" | "http" | "none", "proxyOf"?: ("ios" | "android" | "macos" | "windows" | "linux")[], "build"?: string }[],   // see below
  "env": { "file": string, "derive": string | null, "vars": { "key": string, "kind": "local" | "placeholder" | "secret", "requiredToBoot": boolean, "value": string | null, "note": string | null }[] } | null,   // see below
  "instructions": string | null,               // see below
  "loop": { "name": string, "command": string, "tests": boolean, "affected": string | null }[] | null   // see below
}

Rules: every command runs with `sh -c` at the root of the repository; nothing is assumed about the package manager or the database, so every tool a command needs is named by the command itself. Dependencies are installed against one shared store: use `$CEASELO_PACKAGE_STORE` where the tool takes a store or cache directory. A stack gets its database name in `$CEASELO_DB_NAME` and its ports as the env variables listed in `ports.env`; `readyUrl` may use `{NAME}` for one of those ports. `ports` is null for a repository that serves nothing on a port (a library, a CLI, a native app with no web build), and `db` is null for one without a database. Use null for what neither the repository nor the preset defines.

`surfaces` lists the product surfaces this repository serves (their ids are listed with the product's surfaces in this prompt), each with how a verifier reaches it on the running stack: `browser` for a GUI (its web or PWA target, or a web build of the same UI standing in for its native targets, every one of which is then named in `proxyOf`), `cli` for a command line (the verifier runs the built command and records the transcript), `http` for an API served by `run` (the verifier calls it and records request and response), `none` for what nothing here can drive (a library; a GUI with no web or PWA target only when the preset's text states no web build, and its screens are then checked by hand on a device). `build` only when the surface builds with another command than the repository's `build` (a web build of a native app: `flutter build web`). A GUI surface on web or PWA left without a drive, a native target driven by `browser` but missing from `proxyOf`, or a surface id that is not the product's is refused. List none only for a repository that serves no surface.

`db` holds three shell commands, never names: the machine fills `{template}` with its template database's name and `{db}` with the ticket's. `template` creates database `{template}` and migrates it to the default branch's schema (it runs in a checkout of the default branch); `create` clones `{template}` into `{db}`, so every ticket starts migrated in a fraction of a second; `drop` drops `{db}` if it exists. They reach the database only through the services' ports or their containers, never through a client tool installed on the host (the machine may have no `createdb`, `dropdb` or `psql`): run the database's own client in its container, or a client the repository installs itself. For a Postgres in a container named after `$CEASELO_SERVICE_PROJECT`, for example: `"template": "docker exec db_$CEASELO_SERVICE_PROJECT createdb -U postgres {template} && DATABASE_URL=postgres://postgres:postgres@127.0.0.1:$((CEASELO_SERVICE_PORT_BASE + 2))/{template} pnpm db:migrate"`, `"create": "docker exec db_$CEASELO_SERVICE_PROJECT createdb -U postgres -T {template} {db}"`, `"drop": "docker exec db_$CEASELO_SERVICE_PROJECT dropdb -U postgres --if-exists {db}"`. A contract whose `template` lacks `{template}`, or whose `create` or `drop` lacks `{db}`, is refused.

A test suite that needs a database of its own (a `TEST_DATABASE_URL`, a `*_test` database the test config names) gets one per ticket from the machine: wherever the contract names `{test_db}` (an `env` value, a line `derive` prints, or `$CEASELO_TEST_DB_NAME` in a command), the machine clones a second database from `{template}` with `create`, fills `{test_db}` with its name and drops it with `drop`, so it is already migrated like `{db}`. Point the test config's variable at it as you point the app's at `{db}` (a fixed `value` ending in `/{test_db}`, or `derive` printing `TEST_DATABASE_URL=${DB_URL%/*}/{test_db}`). Every ticket on the machine runs its tests at once, each from its own branch: no command (`db`, a service's `start`, `derive`) may create, migrate or point at a database of a fixed name (`app_test`, the name a compose file or test config defaults to), since every workspace would share, migrate and truncate it together. Only `{db}`, `{template}` and `{test_db}` exist per ticket; `db` commands never name `{test_db}` themselves.

`login` says how every session (captures, builds, verifies) signs in to the app, so none works it out for itself. Find where the app's sign-in lives, then pick one kind:
- `command` when the stack runs its own auth locally: one command the machine runs with `bash -c` on each fresh `{db}` (it fills `{db}`) with the services up, which creates the accounts exactly as the app would and prints one `{"role": string, "email": string, "password": string}` line per account. Create each through the auth service's own API (for a local Supabase, `POST $API_URL/auth/v1/admin/users` with the service-role key and `email_confirm: true`), then add every row the app keeps for a signed-in person in `{db}`: its profile, an organisation or team, its role, and whatever first-run step the app asks of a new account (a display name, accepted terms), so the account lands on the app's own pages, never on an onboarding screen. Where the auth service keeps its users outside `{db}` (a local Supabase keeps them in its own `postgres` database, while `{db}` holds a copy of the `auth` schema the app's tables point to), copy each account's auth row into `{db}` too. It reaches the services as the `db` commands do and must work on a fresh database every time; a `command` without `{db}` is refused.
- `provided` when sign-in runs against a backend this stack does not run (a staging or production API, a hosted auth service): a person gives the accounts. For each account name two `secret` keys in `env.vars` (its email and its password, with a note) and list them in `accounts`; `howTo` tells the person, in plain words, how to make the account (where to sign up or invite, which role to give it).
- `none` when the app has no sign-in.
Give one account with the most privileged role, or one per role (at most 5) when roles see different screens. Sessions get the first account as `$CEASELO_LOGIN_EMAIL` and `$CEASELO_LOGIN_PASSWORD` and every account in `$CEASELO_LOGINS`.

The floor (`verify.steps`) is what every change must pass before its tests, cheapest first, and is refused unless it holds:
- every step has a `kind`: `typecheck`, `build`, `lint`, `test` or `other` (code or project generation, formatting checks);
- a `typecheck` step before the first `lint` step. Use a dedicated typecheck whenever the stack has one (`tsc --noEmit`, `mypy`, `pyright`, `cargo check`, `go vet`); only a compiled stack without a cheaper one uses its compile as a `build` step there (`xcodebuild build`, `swift build`, `gradle compileDebugKotlin`);
- a `lint` step;
- no `test` step before the first `lint` step. Full test suites belong in `test`, which runs after the floor (`test.affected` when it can narrow), not in `verify.steps`.

A step's `affected` is the same check narrowed to what a branch changed since `{base}`, which agents run on every iteration while the floor runs `command`: a workspace filter on changed packages (`pnpm -r --filter "...[{base}]" run lint`), a cached run (`eslint --cache .`), changed-file selection. Only a command the repository's tools support and that checks every change the full command would; null when the stack cannot narrow it.

`toolchain` is what the repository pins, which the machine installs and puts first on PATH for every command: `node` from `.nvmrc`, `.node-version`, `.tool-versions` or `engines.node`, as digits only (`22`, `22.11` or `22.11.0`; for a range such as `>=20` give its lowest major, for `lts/<name>` the major it names, otherwise null); `packageManager` from `package.json#packageManager` as `name@x.y.z` without the `+sha...` suffix (npm, pnpm or yarn only), else null. Set both to null for a repository that is not a Node project. `flutter` is the exact Flutter release (`3.27.1`) from `.fvmrc`, `.fvm/fvm_config.json` or the preset, else null; the machine provisions that SDK (with its own `dart`), so commands call `flutter` and `dart` by name.

`services` lists what the stack needs running on the machine and is not the repository's own server: a local Supabase, a `docker compose up -d` of its databases and queues, as the repository and the preset's text use them. Each runs at the repository root: `start` is idempotent (returns at once when the service is up), `check` exits 0 only while the service answers, `stop` undoes `start` or is null, `memoryMb` is what it holds while running, `needs` is `["docker"]` when it runs containers, `configFiles` lists the repo-relative files a `repo` service reads when it starts (for a local Supabase: `supabase/config.toml`), so a ticket that changes one restarts it from that ticket's checkout. Null when the stack needs no local service.
- `repo` scope: one instance per repository and machine, shared by every ticket, started before the template database is built and kept up while the machine has work for the repository; it is stopped with its `stop` when none is left, and started again when work comes. So a `repo` service's `stop` keeps its data: it stops the containers and leaves their volumes (`supabase stop`, `docker compose stop`, never `down -v`, `--volumes`, `--no-backup` or a `volume rm`), since the template and every ticket's database live there; a stop that drops data keeps the service up for good. The machine may run other projects' services too, so every port it listens on is `$CEASELO_SERVICE_PORT_BASE` plus an offset below 20, and every container, volume or project name it creates includes `$CEASELO_SERVICE_PROJECT`. Isolation never needs a commit to the repository: a tracked config the service reads with fixed ports (a local Supabase's `supabase/config.toml`, a compose file) is copied by `start` into `$CEASELO_SERVICE_DIR` (this machine's directory for the repository's services, outside every checkout), rewritten there for the block and the project name, and run from there; `check` and `stop` use the same directory. For a local Supabase: `start` writes `$CEASELO_SERVICE_DIR/supabase/config.toml` from the tracked one with `project_id` set to `$CEASELO_SERVICE_PROJECT` and each stock port (54321 to 54329) replaced by its own offset in the block, copies `supabase/migrations` beside it, and runs `supabase start --workdir "$CEASELO_SERVICE_DIR"`; `check`, `stop` and `derive` pass the same `--workdir`. Ticket databases are created inside it, so `db` commands and `derive` reach it through those ports.
- `ticket` scope: one instance per ticket, started with the ticket's stack, before `run.command`, inside the ticket's port block (`ports.env` names) and with its database in `$CEASELO_DB_NAME`. Use it for a server whose data must not leak between tickets (for a Supabase preset, the auth and storage servers pointed at the ticket's database), named after `$CEASELO_DB_NAME` so two tickets never share one; `stop` removes it.

`env` is the env file the stack reads, which the machine writes into every checkout before the stack boots and never commits. Distill it from `.env.example` (or `.env.sample`, `.env.template`), the framework's config (Nuxt `runtimeConfig`, Next `NEXT_PUBLIC_*`, Vite `import.meta.env`) and the code that reads `process.env`; null when the stack reads no env at all. `file` is the name the run command loads (`.env.local` when it runs `nuxt dev --dotenv .env.local`, otherwise `.env`). List every key of the example in `vars`:
- `local`: a value of this machine, never asked of a person: local service URLs and keys (Supabase URL, anon and service-role keys, database URLs), site URLs on the stack's own port, flags, and development stand-ins for a shared secret the app only compares with itself (`CRON_SECRET`). Give a fixed `value` when one works on any machine (`{db}` is the ticket's database name, `{test_db}` its test database's and a `ports.env` name in braces its port, for example `http://localhost:{PORT}`), else leave `value` null and print it from `derive`.
- `placeholder`: a third-party key the app only checks the format of while it boots or renders (a tag-manager or analytics id matched against a pattern, a public key a plugin refuses when empty). `value` is a stand-in that passes that check and reaches no real service, read off the code's validation (`GTM-LOCAL0` for `/^(GTM|G)-[0-9A-Z]+$/`). People may still enter the real value on the repo card; it then wins.
- `secret`: a credential of a third-party service only a person has (payment, maps, analytics, error tracking, messaging bots, deployment bypass tokens) that no stand-in can replace. `value` is always null: people enter it on the repo card or on the repository's credentials ticket, which code creates from exactly these keys, so list every third-party credential the code reads (the preset's text and the repository name the providers) under its env name, unless the stack reads it from a local service (then `local`). `note` says in one line where a person gets it ("Stripe dashboard, Developers, API keys").
- `requiredToBoot` is true only when the app does not start or its first page fails without the key; optional analytics, monitoring and integrations are false. `note` says in a few words what the key is for, or null.

`derive` is one shell command, run after `services.start`, that prints `KEY=value` lines for the `local` keys without a fixed value, mapping the service's own output to the repository's names; for a local Supabase, for example: `eval "$(supabase status -o env)" && printf 'NUXT_PUBLIC_SUPABASE_URL=%s\nNUXT_PUBLIC_SUPABASE_KEY=%s\nNUXT_SUPABASE_SECRET_KEY=%s\nNUXT_DATABASE_URL=%s\n' "$API_URL" "$ANON_KEY" "$SERVICE_ROLE_KEY" "${DB_URL%/*}/{db}"`. Null when every local key has a fixed value. A contract with a secret that carries a value, a placeholder without one, a key listed twice, an env file outside the repository, or a required local key with neither a value nor a `derive` is refused.

`instructions` is the repository's instructions, free text on its card that the project's people read and that every agent planning, building, verifying and reviewing its tickets receives and must follow; null only when there is nothing true to say. Clear, readable Markdown, short headings and bullets, at most 80 lines, covering what is true of this repository and only that:
- **Checking a change.** The feedback loop: the actual commands that check nothing is broken, named as runnable commands (for example "Typecheck: `pnpm run typecheck`", "Lint: `pnpm run lint`", "Test: `pnpm run test`"), fastest first; when the repository has one command that runs them all (a preflight, `check` or `ci` script), name it as the check to run before a change is done. Agents run exactly this loop to check their work and the machine's final check runs the same commands, so name only commands that exist in the repository and pass on its code. When the stack can run each check narrowed to what a branch changed (changed packages and their dependents, a cache, related tests), name that form beside it as the one to iterate with, marked as such; the full commands stay the final check.
- **Local database and services**, when the stack has them: what they are (for example a local Supabase with Postgres, Auth and Storage), how a local migration is generated and applied, which the agent does itself, and how migrations reach staging and production, read from the preset, the CI workflows and the deploy configuration. State only what the files and the preset show; when nothing deploys or migrates staging or production, say that it is not set up, never invent one.
- **How to sign in or seed a test account locally, and how to drive the UI** (where it opens, the route to start from), when the stack has a UI.
- A few genuinely useful gotchas, one line each. No trivia an agent finds on its own (an IPv6 localhost, a port of an admin console, how to open a database shell), and nothing the repository's own CLAUDE.md, AGENTS.md or agent docs already say.
No triple-backtick fence.

`loop` is the feedback loop `instructions` states, in its order, each command exactly as written there: `tests` is true for a step that runs the test suite (a preflight that runs the tests counts), `affected` is its narrowed form as written there (a base branch in it becomes `{base}`) or null; null when `instructions` is null or states no check.
