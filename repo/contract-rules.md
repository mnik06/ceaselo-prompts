The command contract is exactly one JSON object of this shape:
{
  "lockfiles": string[],                       // files whose contents decide whether dependencies must be installed again
  "install": string, "build": string,
  "test": { "all": string, "affected": string | null },   // affected may use {base}
  "run": { "command": string, "readyUrl": string | null, "readyTimeoutS": number, "memoryMb": number },
  "deploy": string | null, "deployPreview": string | null,
  "verify": { "steps": { "name": string, "command": string, "kind": "typecheck" | "build" | "lint" | "test" | "other" }[] },   // the floor, in order, fail fast
  "ledgers": { "name": string, "paths": string[], "regenerate": string }[],
  "db": { "template": string, "create": string, "drop": string } | null,   // three shell commands, see below
  "ports": { "block": number, "env": { [ENV_NAME: string]: number } } | null,   // env name -> offset inside the block
  "toolchain": { "node": string | null, "packageManager": string | null, "flutter": string | null },  // see below
  "services": { "name": string, "scope": "repo" | "ticket", "start": string, "check": string, "stop": string | null, "memoryMb": number, "needs": ("docker")[] }[] | null,   // local dependencies the stack needs running, see below
  "env": { "file": string, "derive": string | null, "vars": { "key": string, "kind": "local" | "placeholder" | "secret", "requiredToBoot": boolean, "value": string | null, "note": string | null }[] } | null,   // see below
  "instructions": string | null                // see below
}

Rules: every command runs with `sh -c` at the root of the repository; nothing is assumed about the package manager or the database, so every tool a command needs is named by the command itself. Dependencies are installed against one shared store: use `$CEASELO_PACKAGE_STORE` where the tool takes a store or cache directory. A stack gets its database name in `$CEASELO_DB_NAME` and its ports as the env variables listed in `ports.env`; `readyUrl` may use `{NAME}` for one of those ports. `ports` is null for a repository that serves nothing on a port (a mobile app, a library, a CLI), and `db` is null for one without a database. Use null for what neither the repository nor the preset defines.

`db` holds three shell commands, never names: the machine fills `{template}` with its template database's name and `{db}` with the ticket's. `template` creates database `{template}` and migrates it to the default branch's schema (it runs in a checkout of the default branch); `create` clones `{template}` into `{db}`, so every ticket starts migrated in a fraction of a second; `drop` drops `{db}` if it exists. For Postgres, for example: `"template": "createdb {template} && DATABASE_URL=postgres://localhost/{template} pnpm db:migrate"`, `"create": "createdb -T {template} {db}"`, `"drop": "dropdb --if-exists {db}"`. A contract whose `template` lacks `{template}`, or whose `create` or `drop` lacks `{db}`, is refused.

The floor (`verify.steps`) is what every change must pass before its tests, cheapest first, and is refused unless it holds:
- every step has a `kind`: `typecheck`, `build`, `lint`, `test` or `other` (code or project generation, formatting checks);
- a `typecheck` step before the first `lint` step. Use a dedicated typecheck whenever the stack has one (`tsc --noEmit`, `mypy`, `pyright`, `cargo check`, `go vet`); only a compiled stack without a cheaper one uses its compile as a `build` step there (`xcodebuild build`, `swift build`, `gradle compileDebugKotlin`);
- a `lint` step;
- no `test` step before the first `lint` step. Full test suites belong in `test`, which runs after the floor (`test.affected` when it can narrow), not in `verify.steps`.

`toolchain` is what the repository pins, which the machine installs and puts first on PATH for every command: `node` from `.nvmrc`, `.node-version`, `.tool-versions` or `engines.node`, as digits only (`22`, `22.11` or `22.11.0`; for a range such as `>=20` give its lowest major, for `lts/<name>` the major it names, otherwise null); `packageManager` from `package.json#packageManager` as `name@x.y.z` without the `+sha...` suffix (npm, pnpm or yarn only), else null. Set both to null for a repository that is not a Node project. `flutter` is the exact Flutter release (`3.27.1`) from `.fvmrc`, `.fvm/fvm_config.json` or the preset, else null; the machine provisions that SDK (with its own `dart`), so commands call `flutter` and `dart` by name.

`services` lists what the stack needs running on the machine and is not the repository's own server: a local Supabase, a `docker compose up -d` of its databases and queues. Every approved service of the repository that runs locally is listed under exactly its name and scope; a contract that drops or renames one is refused. Each runs at the repository root: `start` is idempotent (returns at once when the service is up), `check` exits 0 only while the service answers, `stop` undoes `start` or is null, `memoryMb` is what it holds while running, `needs` is `["docker"]` when it runs containers. Null when the stack needs no local service.
- `repo` scope: one instance per repository and machine, shared by every ticket, started before the template database is built and kept up. The machine may run other projects' services too, so every port it listens on is `$CEASELO_SERVICE_PORT_BASE` plus an offset below 20, and every container, volume or project name it creates includes `$CEASELO_SERVICE_PROJECT` (for a local Supabase: a `supabase/config.toml` whose `project_id` and ports read those variables). Ticket databases are created inside it, so `db` commands and `derive` reach it through those ports.
- `ticket` scope: one instance per ticket, started with the ticket's stack, before `run.command`, inside the ticket's port block (`ports.env` names) and with its database in `$CEASELO_DB_NAME`. Use it for a server whose data must not leak between tickets (for a Supabase preset, the auth and storage servers pointed at the ticket's database), named after `$CEASELO_DB_NAME` so two tickets never share one; `stop` removes it.

`env` is the env file the stack reads, which the machine writes into every checkout before the stack boots and never commits. Distill it from `.env.example` (or `.env.sample`, `.env.template`), the framework's config (Nuxt `runtimeConfig`, Next `NEXT_PUBLIC_*`, Vite `import.meta.env`) and the code that reads `process.env`; null when the stack reads no env at all. `file` is the name the run command loads (`.env.local` when it runs `nuxt dev --dotenv .env.local`, otherwise `.env`). List every key of the example in `vars`:
- `local`: a value of this machine, never asked of a person: local service URLs and keys (Supabase URL, anon and service-role keys, database URLs), site URLs on the stack's own port, flags, and development stand-ins for a shared secret the app only compares with itself (`CRON_SECRET`). Give a fixed `value` when one works on any machine (`{db}` is the ticket's database name and a `ports.env` name in braces its port, for example `http://localhost:{PORT}`), else leave `value` null and print it from `derive`.
- `placeholder`: a third-party key the app only checks the format of while it boots or renders (a tag-manager or analytics id matched against a pattern, a public key a plugin refuses when empty). `value` is a stand-in that passes that check and reaches no real service, read off the code's validation (`GTM-LOCAL0` for `/^(GTM|G)-[0-9A-Z]+$/`). People may still enter the real value on the repo card; it then wins.
- `secret`: a credential of a third-party service only a person has (payment, maps, analytics, error tracking, messaging bots, deployment bypass tokens) that no stand-in can replace. `value` is always null: people enter it on the repo card or on the service's credentials ticket. Every secret the repository's approved services declare is a `secret` here under its env name, unless the stack reads it from a local service (then `local`); code adds one you leave out.
- `requiredToBoot` is true only when the app does not start or its first page fails without the key; optional analytics, monitoring and integrations are false. `note` says in a few words what the key is for, or null.

`derive` is one shell command, run after `services.start`, that prints `KEY=value` lines for the `local` keys without a fixed value, mapping the service's own output to the repository's names; for a local Supabase, for example: `eval "$(supabase status -o env)" && printf 'NUXT_PUBLIC_SUPABASE_URL=%s\nNUXT_PUBLIC_SUPABASE_KEY=%s\nNUXT_SUPABASE_SECRET_KEY=%s\nNUXT_DATABASE_URL=%s\n' "$API_URL" "$ANON_KEY" "$SERVICE_ROLE_KEY" "${DB_URL%/*}/{db}"`. Null when every local key has a fixed value. A contract with a secret that carries a value, a placeholder without one, a key listed twice, an env file outside the repository, or a required local key with neither a value nor a `derive` is refused.

`instructions` holds the repository's feedback loops for the agents that plan, build, verify and review tickets here, or null when there is nothing to add: exactly one `## Feedback loops` section and nothing else, at most 40 lines of `- ` bullets, one fact per bullet. Cover, in this order: how to check a change here, fastest check first (one test file, one package's typecheck, the affected tests); how to run the stack and its local services; how to sign in or seed a test account locally; how to drive the UI (where it opens, the route to start from). Write only what the preset and the files support. Name a contract command only to add what it lacks (a narrower form, a flag, a port), never to repeat it, and never restate what the repository's own CLAUDE.md, AGENTS.md or agent docs already say. Layout, conventions and traps belong in those docs, never here. No other heading, no prose paragraph, no triple-backtick fence.
